## 해설강의에서 인상깊었던 점

### 1. 코드를 예측하는 것이다

**코드는 읽는게 아니라 예측하는 것이다** 라는 말을 해주셨는데, 갑자기 내가 코드를 볼때 어려운 점이 떠올랐다.

맥락을 전혀 알지 못하는 오픈소스 소스코드를 볼때 가장 어려운 점을 생각해보면

1. 한줄씩 읽으면서 내려감. 뭔가 파악이 되는거 같음. 그러다 a라는 함수가 다른파일에있음 - 이걸 보고옴- 매우 복잡해서 읽고 돌아와보니 위에있던 코드들이 기억이 안남.. 하지만 일단 넘어감
2. b라는 변수가 알고보니 방금 봤던 더 위에있는 코드랑 관련이 있음. 또 보고옴
3. 또다시 c라는 걸 알려면 a를 또 알아야됨. 근데 까먹었음.

만약 이때 a라는 함수가 예측하기 쉬웠다면? 예를들어서 특정값들을 더하는 역할을 하는 함수였는데, 함수명이 `add(더할 요소들)` 이렇게 되어있었다면?
함수의 디테일한 구현은 당장 기억하고 있지 않아도
다음 코드에서 a가 나와도 '아 이거 ~ 더한값이었지' 이런식으로 넘어갈 수 있을 것이다.

물론 도메인을 다루게 되는 순간 이렇게 작성하는 게 너무 어려워지는 건 분명한 것 같다.
하지만 최소한 어느정도 맥락을 가지고 있는 사람을 대상으로, 어느정도 파악을 할 수 있게끔 코드를 작성하는게 최선의 선택이지 않을까 싶다.

### 2. 인터페이스는 사용되는 곳을 고려하는 게 아니라, 그 자체의 의미를 담고있는게 중요하다.

컴포넌트 자체에 대한 interface를 설계한 뒤 props로 전달하는게아니라 애초부터 이 컴포넌트가 사용될 곳을 고려해서 interface를 설정하는 경우를 굉장히 많이 보는데(특히 setData 같은거 props로 넘기는거) 정작 이게 왜 잘못되었는지에 대해서 명확하게 설명할 수는 없었는데, 이런 관점에서 바라볼 수 있을 것 같다.

### 3. 근거를 가지고 코드를 작성하자.

어차피 코드라는 건 정답이 없기 때문에, 내가 이 코드를 이렇게 작성하게 된 근거를 댈 수 있으면 된다는 말이 되게 인상깊었다.

### 개인적인 후기

그래도 1차 모의고사보다 조금 나아졌다고 생각한 부분은 스스로의 판단력이 생겼다는 부분인 것 같다.

input들이 모여있는 섹션이 있고, input 데이터들을 기반으로 리스트 데이터를 필터링해서 보여주는 페이지를 구현해야 하는데, 페이지의 흐름상 `<FilterPanel>` `<BookingList>` 이런식으로 나누는 것을 먼저 생각했지만, 이렇게 될 경우

`FilterPanel` 에서 선택된 데이터들을 -> 루트 페이지에 전달해서 -> 이 데이터를 또 `BookingList`에 전달을 해야되는데, 그럼 `FilterPanel` 의 인터페이스를 어떻게 해야하는지?
필요한 데이터를 생각해보면 `data, setData, input1에대한 정규화옵션, input2에대한 onChange이벤트...` 들이 필요해지는데, 이런 인터페이스들을 뭔가 명확하게? 적용하는 방법이 사실 잘 생각나진 않았다. 오히려 이걸 읽는사람 입장에서 의미 파악이 잘 되지 않을것 같다는 생각이 들었다.

그래서 나는 과감하게 아무것도 추상화하지 않았다.
그러다 보니 코드도 길고, 큰 변경점이 생기지 않아서 내가 잘못하는건가 하는 생각이 들긴 했지만 해설을 듣고 나니 내가 한 판단이 잘못된 건 아니었던 것 같다.

2. 명확한 관점,의도를 가지고 코드를 바라보니 좀 방법이 보였다.
   내가 가장 어려웠던 파트는 url을 기반으로 전역상태를 만들고 -> 상태를 변경하면 다시 url을 변경시키고 하는 url을 상태의 ssot로 바라보는 게 필요했는데

- url에 invalid한 값이 들어오는것에 대비(validation 및 fallback 값으로 대체)
- 상태를 다시 url로 업데이트하기 위한 정규화

이런걸 다 다루려다 보니, 나도 모르게 `useBookingFilter()` 같은, 아무도 알아볼 수 없는 custom hook이 완성되어가고 있었고,
이번 과제에 큰 시간을 투자하지 못해서 이런 상태로 제출하게 되어버렸는데.. 해설강의를 듣고나서 지금 내가 무슨 의도를 가지고 이걸 하는지를 돌이켜보고 이를 기반으로 리팩토링을 했다.

처음 코드를 보는사람이 이 페이지에서 다루고 있는 필터링 데이터 상태가 url을기반으로 하는지, 내부의 도메인 로직 같은걸 몰라도 그냥 `useState()` `setState()` 처럼 쓰이고 있구나 라는 것만 알게 하는 것을 목적으로 제작했는데, hook내부 코드를 보면

```ts
export const useBookingFilter = (constraint: BookingFilterConstraint) => {
  const [searchParams, setSearchParams] = useSearchParams()
  const queryString = searchParams.toString()
  const constraintKey = `${formatDate(constraint.date)}|${constraint.floor.join(",")}`

  const normalizedFromUrl = useMemo(() =>
    // queryString에 대해서 validation 및 fallback값으로 대체하는 아주 긴 로직..
    [constraintKey, queryString],
  )

  const [value, setValue] = useState<BookingFilter>(normalizedFromUrl)

  useEffect(() => {
    setValue(normalizedFromUrl)
  }, [normalizedFromUrl])

  useEffect(() => {
    const nextQuery = qs.stringify(
      {
        date: value.date,
        startTime: value.startTime || undefined,
        endTime: value.endTime || undefined,
        attendees: value.attendees > 1 ? value.attendees : undefined,
        equipment:
          value.equipment.length > 0 ? value.equipment.join(",") : undefined,
        floor: value.preferredFloor ?? undefined,
      },
      {
        skipNulls: true,
      },
    )

    if (nextQuery !== queryString) {
      setSearchParams(nextQuery, { replace: true })
    }
  }, [queryString, setSearchParams, value])

  return {
    value,
    updateValue: (patch: Partial<BookingFilter>) => {
      setValue((previous) => ({
        ...previous,
        ...patch,
      }))
    },
    setValue,
  }
}
```

일단 이 hook에 문제가생기거나 정책이 바뀐다면, '어디를 건드려야 할지'를 파악하기가 너무 어려울 것 같다는 생각이 들었다.
왜일까 고민을 좀 해보니
현재 이 hook에는 url을 읽어서 상태처럼 다루고, 업데이트하는 로직과 , validation , normalize가 섞여있다.
이 세개를 하나의 hook에서 다루는 게 문제라기 보다는, 책임이 다른 로직들이 너무 경계없이 하나처럼? 다뤄진다는게 문제라고 생각이 들었다.

1. url을 상태처럼 다루는 로직은 저렇게 특정 도메인을 아는 것보다, nuqs의 useUrlState처럼 범용적인 hook을 활용할 수 있을 것 같았다.

- 처음에는 `nuqs` 를 쓰려고 했으나 많이 사용해본 적이 없어서 간단한 버전으로 만들어서 사용해봤는데, nuqs를 쓰면 url state뿐만 아니라 파싱 관련 처리도 라이브러리 api를 통해 처리할 수 있지 않을까 싶으면서도, 너무 특정 라이브러리에 종속되는건 아닐까 싶긴 하다.

2. 두번째로 url에 대한 validation+fallback으로 대체하는 로직을 좀 더 잘 다뤄볼 수 있지 않을까 하는 생각이 들었고, zod를 활용했다.

- 사용하게 된 계기는, 그리고 사실 UI의 요구사항이 필터인거지 어떻게 보면 이것도 Form이니까, Form의 validation처럼 다루면 되지 않을까? 하는 생각이 들었다.

- 개인적으로 zod라는 라이브러리를 좋아하는데, 실제 기능 뿐만 아니라, 타입 SSOT를 잘 지켜주기 때문인것도 있다. 굳이 두 벌의 타입을 선언하지 않아도 schema로 파생된 타입을 쓸수있다.

- Form validation을 zod로 하면 제약사항을 응집력 있게 관리할 수도 있고, 굳이 `||` 이런걸 쓰지 않아도 fallback에 대한 것도 깔끔하게 처리 가능하다.

- AI가 zod를 굉장히 잘쓰는 것 같다(대신 3버전 한정..).
- 여기서 조금 고민한 건 요구사항에 따라 schema를 정적으로 만들어놓을 수 없어서 동적으로 만들게 되었는데 이게 맞는지 잘 모르겠다

3. 마지막으로 qs.stringify()를 하는 로직도, 저렇게 펼쳐놓지말고 normalize()라는 로직으로 추상화해놓으면 나중에 hook 코드를 보는 사람이 의도를 좀더 잘 파악할 수 있지 않을까? 하는 생각이 들었다

완성본

```ts
import { useEffect } from "react"
import { z } from "zod"
import { useUrlState } from "../../../hooks/useUrlState"

import { ALL_EQUIPMENT } from "../../../reservation/equipment"
import {
  createTimeSlots,
  TIMELINE_END,
  TIMELINE_START,
} from "../../../reservation/schedule"

export type BookingFormContext = {
  floors: number[]
  date: string
}

export type BookingFormParams = {
  date?: string
  startTime?: string
  endTime?: string
  attendees?: string
  equipment?: string
  floor?: string
}

const TIME_SLOTS = createTimeSlots(TIMELINE_START, TIMELINE_END)
const START_TIME_SLOTS = TIME_SLOTS.slice(0, -1)
const END_TIME_SLOTS = TIME_SLOTS.slice(1)
const DATE_PATTERN = /^\d{4}-\d{2}-\d{2}$/

export const createBookingFormSchema = (context: BookingFormContext) => {
  return z
    .object({
      date: z
        .string()
        .regex(DATE_PATTERN)
        .refine((value) => value >= context.date)
        .catch(context.date),
      startTime: z
        .string()
        .refine((value) => value === "" || START_TIME_SLOTS.includes(value))
        .catch(""),
      endTime: z
        .string()
        .refine((value) => value === "" || END_TIME_SLOTS.includes(value))
        .catch(""),
      attendees: z.coerce.number().int().min(1).catch(1),
      equipment: z
        .string()
        .catch("")
        .transform((value) =>
          value
            .split(",")
            .filter((item): item is (typeof ALL_EQUIPMENT)[number] =>
              ALL_EQUIPMENT.includes(item as (typeof ALL_EQUIPMENT)[number]),
            ),
        )
        .transform((value) => Array.from(new Set(value))),
      floor: z
        .string()
        .catch("")
        .transform((value) => (value === "" ? null : Number(value)))
        .pipe(
          z
            .number()
            .int()
            .refine(
              (value) =>
                context.floors.length === 0 || context.floors.includes(value),
            )
            .nullable()
            .catch(null),
        ),
    })
    .transform(({ floor, ...value }) => ({
      ...value,
      equipment: value.equipment,
      preferredFloor: floor,
    }))
}

export type BookingForm = z.infer<ReturnType<typeof createBookingFormSchema>>

export const serializeBookingForm = (
  value: BookingForm,
): BookingFormParams => ({
  date: value.date,
  startTime: value.startTime === "" ? undefined : value.startTime,
  endTime: value.endTime === "" ? undefined : value.endTime,
  attendees: value.attendees > 1 ? String(value.attendees) : undefined,
  equipment: value.equipment.length > 0 ? value.equipment.join(",") : undefined,
  floor:
    value.preferredFloor == null ? undefined : String(value.preferredFloor),
})

export function useBookingState({ context }: { context: BookingFormContext }) {
  const { value: params, setValue: setParams } =
    useUrlState<BookingFormParams>()
  const value = createBookingFormSchema(context).parse(params)
  const normalizedParams = serializeBookingForm(value)

  useEffect(() => {
    setParams(normalizedParams, { replace: true })
  }, [normalizedParams, setParams])

  const setValue = (patch: Partial<BookingForm>) => {
    setParams(serializeBookingForm({ ...value, ...patch }), { replace: true })
  }

  return {
    value,
    setValue,
  }
}
```
